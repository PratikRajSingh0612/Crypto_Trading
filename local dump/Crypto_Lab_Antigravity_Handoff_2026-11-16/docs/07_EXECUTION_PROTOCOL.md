# 7. Streamlined Antigravity-only execution

## Roles, not another controller

The primary Antigravity agent coordinates the programme, reads accepted contracts, selects tasks and records decisions. One implementation context owns each active worktree. A separate reviewer context inspects the candidate and test evidence. Deterministic tools establish exits, identities and test results. Do not rebuild the retired Python controller merely under a new provider name.

## Ready-task selection

A task is READY when its scope, interfaces, owner, environment, test route and integration target are known. Existing accepted plans remain the behavioral basis. For genuinely unplanned projects, create one compact just-in-time plan and have it independently reviewed; do not generate thousands of purported approved tasks upfront.

First finish useful preserved work. Prioritize P1 completion and the first one-engine research release. Use a spare writer for independent P2/P3 work that does not change the same contracts. Do not fill spare capacity with endless readiness reports or easier documentation merely to show activity.

## Per-task cycle

1. Read the exact task and current implementation. Reconcile amendments once. Identify success/failure behavior, contract consumers and the whole candidate path set.
2. Confirm execution readiness before consuming a coding attempt: intended branch/cwd, dependency environment, supported command route, source permissions and publication destination.
3. Add a focused failing regression/test for new behavior. Implement minimally. Run focused tests and applicable lint/type/schema/migration checks.
4. Make one consistent candidate. Review the entire actual delta with relevant requirements. Fix material findings; re-review the changed behavior and closure of prior findings, not unrelated accepted code.
5. Run the required authoritative acceptance on the final subject. Retain coverage and skip policies. Do not run duplicate full suites against unchanged bytes without a separate purpose.
6. Stage the exact accepted files, check the staged diff, commit, confirm parent/tree and publish the explicit intended branch under the standing authorization.
7. Checkpoint actual outcome and select the next READY task. Do not stop just because the old controller would have needed another turn/gate token.

## Procedural autonomy

Resolve harmless plan wording conflicts, complete file-map omissions within scope, grouping of related corrections, and known Git/publication reconciliation autonomously. Record the changed procedural clause, rationale and invariant preserved. Do not turn a procedure into a reason to overwrite work or violate a product guarantee.

A changed schema, migration or economic behavior requires an explicit owner-stage correction with consumer impact and real tests. The programme's broad local-development mandate permits planning and engineering that work; it does not turn a mock or skipped criterion into acceptance.

## Test scheduling

Focused tests run during implementation. Broader consumer tests follow relevant changes. Full verification runs at actual required acceptance checkpoints. Existing task-level requirements are not silently replaced by cross-task batching. A justified scheduling amendment must be prospective and record which intermediate commits are full-regression-pending.

On this host, one full suite/process-heavy test owner at a time. During its window: no edits of the verified tree or toolchain, no competing controller suite, installation, engine benchmark, local LLM or review swarm. Heavy-job idleness does not require stopping a lightweight task in a completely separate environment if resource/ownership rules allow it.

## Checkpoint and recovery

Before context/session/quota boundaries, write: active task, base and tree/diff identities, completed behaviors, actual commands/results, open findings, exact next action and active process/lock ownership. Keep untracked bytes. Resume from this record and inspect real state before replaying a commit or push.

A completed command without an exit record is not a pass. A prior task ACCEPTED event cannot justify a different tree. A successful push interrupted before the checkpoint must be reconciled from the actual remote ref, not repeated with a duplicate commit.

## Limits and backoff

Legacy monetary/retry/turn quotas are archived, not new Antigravity policy. Real account quota and OS permissions remain. Avoid blind retry loops: unchanged failures call for diagnosis or a genuinely bounded environmental retest with retained outcomes. Long test runtimes are not automatically hangs; use existing per-command semantics and evidence, not arbitrary new timeouts.

## Reporting

Report accepted product capabilities, actual state, next dispatch, evidence and remaining blockers. Do not report continuous 'still waiting' messages. Do not claim a process is running without observation. Keep estimates separate from facts, and do not calculate overall completion from unequal project/task counts.
