# 6. One-time takeover and retirement of the old controllers

## Principle

Take over the existing product; do not rebuild it and do not run a second writer against the same state. Retiring a provider relay is not deleting its evidence, installed software, credentials or accepted product commits.

## A. Read-only intake

Resolve the actual Git root, all worktrees, branches, complete HEADs, index states and dirty/untracked files. Check whether local main really contains `6678c15`, whether its verifier completed and what the remote currently names. Preserve S10-T1 and any T2 work even if it is not on main.

Inspect the former `Crypto_Lab_Dev_Controller` and `Crypto_Lab_Dev_Controller_P2` roots as historical data. Read the current checkpoint, source-linked journal events, review/verifier records, host lock ownership and STOP/PAUSE state. Do not launch their `run.py` entrypoints or ask their AI advisors to approve the new handoff.

Identify processes by their actual owner, creation identity, working context and known task records. Do not infer an idle machine from an expired monitor, a dead shell or a PID disappearing later. Avoid publishing command lines that contain credentials. The local collector intentionally does not dump process arguments or environment values.

## B. Quiesce deliberately

Request no new dispatch at the supported stop boundary. Let an already-running authoritative verifier finish when practical and retain its complete outcome. Do not change its subject or toolchain during execution. If interruption is necessary, record INTERRUPTED, not FAILED/PASSED, retain partial logs and ownership-aware cleanup.

Gracefully stop each positively identified legacy supervisor and its owned watcher tree. Do not terminate unrelated applications, security tools or other sessions. Check that no autostart/scheduled relaunch remains enabled for the old mission; change only the specific known registration, not system-wide startup policies.

Never run Antigravity writes concurrently with an active former controller writer. Do not delete an unfamiliar lock; inspect its owner and recorded release policy.

## C. Preserve before retirement

Archive the relevant current checkpoints, journals, accepted manifests, verifier logs, review records, task/scope amendments, exact controller commits, outstanding observations and partial product diffs. Keep private logs local. Do not bundle credentials, environment dumps, browser profiles or model API keys.

Record a takeover manifest: repository/worktree roots, complete refs, dirty path sets, active/inactive process evidence, last acceptance identity and new next task. A Git diff alone does not preserve untracked files; copy their actual bytes into the private checkpoint without moving originals.

Old controller code is read-only reference after retirement. Do not delete the repositories, uninstall software or revoke credentials as an implicit migration step. Those actions are unnecessary to stop future provider use.

## D. Antigravity policy adaptation

Activate only Google models and supported Antigravity routes. Review current `AGENTS.md`, nested rules and task plans. Distinguish enduring product contracts from former controller-only mechanics (allowlist keys, relay state names, provider-specific hook forms, turn ceilings and pilot campaigns).

Write one prospective local-development amendment documenting which mechanics are replaced by direct Antigravity operation and what evidence/gates remain. Do not falsify old plan acceptance or rewrite historical outcomes. Apply precise behavior-preserving documentation/guard reconciliation where needed instead of repeatedly asking the owner about obsolete controller paths.

The rule templates in this package are inert under `templates/`. Install only the relevant root-level `.agents/rules/*.md` files after inspecting inherited rules. Verify the installed application loads them. Rules are cumulative; do not assume one new file disables contradictory old instructions or enforces permissions at the OS layer.

## E. Readiness proof

A small disposable test should establish the actual selected tool permissions and repository access, using synthetic files rather than product secrets. Confirm that a reviewer can remain read-only through the supported configuration. Use Antigravity's real permission UI; never bypass a denied OS/platform operation with an alternative shell or encoding.

Verify the existing product execution route and cwd, using the least expensive relevant read-only discovery/check. Do not reinstall environments or rerun a full baseline just because the IDE changed if the preserved subject and execution evidence remain valid. A changed toolchain or acceptance-required check must receive the relevant fresh evidence.

## F. Activate exactly once

Record that legacy dispatch is retired, no conflicting writers remain, and the authoritative product subject is known. Start one Antigravity implementation task and at most one independent nonoverlapping secondary task. Review is a separate context, not a new provider relay. Keep one heavy test owner across all worktrees.

The next task is selected from real current plans, not this snapshot's guessed chronology. If T2 has already landed, advance. If an integration is awaiting its final gate, finish/reconcile it rather than recreate it. If only a schema blocker remains, plan its owning-stage correction rather than declaring Project 1 done.

## Rollback of the migration

On an Antigravity tooling failure, checkpoint and stop its owned work. Do not automatically reactivate Claude/Codex; the owner explicitly retired them. Product history and private evidence remain available. Use another supported Google/Antigravity route only within the user's available permissions, or report the exact environmental blocker.
